# 询问 Matt

你不可能记住每一个 skill，所以要主动问。

**流程（flow）** 是一条穿越各 skill 的路径。绝大多数路径沿着一条**主流程**行进，并且有两条**接入支线（on-ramps）**汇入其中。其余的要么是独立的，要么是运行在其下方的"词汇层"。

## 主流程：想法 → 发布

绝大多数工作都会走这条路。你有了一个想法，并希望把它构建出来。

1. **`/grill-with-docs`** 通过访谈来打磨想法。每当你在**工作目录（working directory）** 中工作时都从这里开始：它是有状态的，会把它学到的东西保留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见"独立 skill"一节。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 是会留下书面记录的那个，因此只要有仓库可以留痕，它就是更好的选择。）
2. **分支判断：你能否在对话中解决所有问题？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、一个必须看到的 UI），那就绕道原型（prototype）来回走一趟，两端都用 **`/handoff`** 桥接（原型存在于自己的目录里，这正是 `/handoff` 的用途；见"阶段边界"一节）：
   - **`/handoff`** 把当前状态交接出去，然后在那个文件下开一个新会话，
   - 用 **`/prototype`** 用一次性代码来回答那个问题，
   - 然后 **`/handoff`** 把学到的东西带回来，并在原始的想法讨论串里引用它。
3. **分支判断：这是一个多会话的构建任务吗？**
   - **是** → **`/to-spec`**（把讨论串变成 spec），再用 **`/to-tickets`** 把它拆成"示踪弹"（tracer-bullet）形式的工单，每张工单声明自己的**阻塞边（blocking edges）**。如果是本地跟踪器，则在 `.scratch/<feature>/issues/` 下每张工单一个文件，按阻塞顺序手工处理；如果是真正的跟踪器，阻塞边则变成原生的阻塞链接，这样任何阻塞都已解除的工单就可以被领取：每张工单启动 **`/implement`**，在每张工单之间用 **`/clear`** 清空上下文。每张工单都是自包含的，所以最后一张工单的上下文用完即可丢弃。
   - **否** → 就在当前同一上下文窗口里直接用 **`/implement`**。

   无论哪种情况，**`/implement`** 都是通过内部驱动 **`/tdd`**（一次一片红绿切片）来构建每个 issue，最后在提交前运行一次 **`/code-review`**（两轴——标准 + Spec——对 diff 的评审）作为收尾。当你只想测试先行地构建某个具体行为、而无需完整 spec 时，可以单独使用 **`/tdd`**；当你希望针对某个固定基线评审分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生

把第 1–3 步保持在**同一个不中断的上下文窗口里**（在 `/to-tickets` 完成之前不要 compact 或 clear），这样访谈、spec 和工单都能建立在同一套思考之上。然后每轮 `/implement` 都从一张工单开始、从零起步。

这一做法的上限是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型在窗口内（约 150k token，当前最先进模型）仍然能保持敏锐推理的范围。如果某个会话在抵达 `/to-tickets` 之前就已逼近该上限，不要在性能下降的状态下硬撑；在最近的阶段边界处 `/compact` 一下，然后继续（见"阶段边界"）。

## 接入支线（On-ramps）

由某个起始情境生成工作，然后汇入主流程。

- **缺陷报告和需求请求堆积如山** → **`/triage`**。它把 issue 沿着分诊角色推进，并产出 agent-ready 的 issue，供稍后的 **`/implement`** 接走。

  Triage 仅适用于**不是由你创建的** issue：bug 报告、外部涌入的功能请求、任何"原样"到来的东西。`/to-tickets` 产出的工单已经是 agent-ready 的，所以**不要**再对它们做 triage。

- **什么东西坏了** → **`/diagnosing-bugs`**。专治硬骨头：一眼看不出来的 bug、间歇性抽风、在两个已知良好状态之间偷偷溜进来的回归。它会拒绝在掌握一个**紧凑反馈环**（一条已经能在这个 bug 上变红的命令）之前做任何理论假设，然后用一个回归测试来修复。它的复盘会把"真正原因是这里没有一个好的接缝（seam）能把 bug 锁住"的情况交给 **`/improve-codebase-architecture`**。

- **一项巨大、模糊的工程：绿地项目，或者一项大到塞不进单个会话的大功能构建** → **`/wayfinder`**，本套件里认知负荷最高的一条流程。当"从这里到目的地"的路还看不见时，它会在 issue tracker 上画出一张**共享地图**，由一个个**决策工单（decision tickets）** 组成，逐个解决，产出的是**决策而非交付物**，直到迷雾被推回、路径变得清晰。**`/grill-with-docs`** 用于打磨你能在一次会话内把握的想法；wayfinder 则用于那种你把握不住的想法，而且它更慢、信息密度更大，所以只在确实必要时才用它，永远不要用在范围明确的小功能上。

  当地图变得清晰时，它**只交接、不构建**：在 **`/to-spec`** 处汇入主流程，那里会把地图上相互关联的决策压缩成可构建的计划，然后照常 `/to-tickets` 和 `/implement`。如果绕过这一步直接把地图送进 `/implement`，就会丢掉那套相互关联的细节，所以只有当工程最终确实很小时才直接走 `/implement`。

## 代码库健康

不是新功能的工作，只是日常维护。

- **`/improve-codebase-architecture`**：当你有一点空闲时间、希望让代码库对 agent 更友好时运行它。它会浮现**深化机会（deepening opportunities）**；挑中一个，就会**生成一个想法**，可以在 `/grill-with-docs` 处带入主流程。它是一份"勘测"，负责找出候选；下面的 **`/codebase-design`** 则是你为所选候选做设计的工作台。

## 底层词汇层

两个被模型调用的参考层，运行在*其他 skill 之下*，各自都是其词汇的唯一真相之源。当问题出在**用词**本身、而非流程时，直接调用它们；或者让上面的 skill 自动把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：挑战一个模糊的术语、解决一个被滥用的词（"account" 干了三件事）、把一条难以撤回的决策记录为 ADR。它是 `/grill-with-docs` 用来保持 `CONTEXT.md` 干净词表的积极纪律。
- **`/codebase-design`** 是深模块（deep module）词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计一个模块的*形状*：用小接口在大接缝背后承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都讲这套词汇。

## 阶段边界

**阶段（phase）** 是会话内部的一段工作块：访谈、实现、QA。在两个阶段的**边界（boundary）** 处，你有五种选择，而这是整张地图中最模糊的决策：

- **Continue（继续）**：原地不动。不花钱，也无所失。
- **`/clear`**：清空窗口，当这里的东西对下一步毫无意义时。
- **`/handoff`**：写出一份可移植的 markdown 文件。范围很窄：仅用于**新的 harness**、**新的目录**、**同事**，或者在**阶段中途**分叉出一个旁支任务。它换来的是可移植性。
- **子 agent（Subagent）**：把一个范围紧凑的任务派到它自己的窗口里，拿一份报告回来。
- **`/compact`**：压缩当前上下文，并在新会话中以它为种子。**默认**选项，处于决策树最底部，而不是第一反应。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以了解有序的决策树：五个问题、每个分支背后的推理，以及为什么"主源成本"会让 **Continue** 成为第一个应当被排除的选项。**在**边界处做这个决策；阶段进行到一半时，要么继续，要么把剩余部分拆成子 agent。

## 独立 skill（Standalone）

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 同样不依不饶的访谈，但**无状态**：本地不保存任何东西，也不生成 `CONTEXT.md`。在你**不在工作目录中**时调用它（打磨一份计划、一个设计、一段文字，任何下面没有仓库的东西）。如果你在工作目录里，请改用 `/grill-with-docs`：它跑的是同一套访谈，但会留下书面记录，因此严格来说是更好的选择。
- **`/grilling`** 本身就是访谈原语：轮次、前沿、由 agent 负责事实、由你负责决策。`/grill-me` 和 `/grill-with-docs` 是两个有名字的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都会在内部运行它。仅当你想要"不带任何外包装的访谈"时才直接调用它。
- **`/resolving-merge-conflicts`**：一段一段地处理进行中的 merge 或 rebase 冲突，依据各方**主源**回溯到**意图**来解决，而不是挑行；然后收尾操作。它**绝不**运行 `--abort`。独立使用，不在任何一个流程里：当你已经处于冲突中时调用它。
- **`/prototype`** 是一个小而临时的程序，用来回答一个设计问题：这个状态模型感觉对不对？这个 UI 应该长什么样？"临时"是对代码写法的约束，而非一定会销毁的承诺：答案会被折回真实代码，而原型本身会被作为**主源**保留在从 main 分出的 `prototype/<name>` 分支上，并在实现 issue 中被引用。它是主流程第 2 步中的那段绕行，但任何设计问题在纸面上难以敲定时，都可以调用它。
- **`/research`**：把阅读杂活委派给一个**后台 agent**：它针对**主源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。你可以一边工作、一边等它读完。它产出的那份文件，是要**带入**主流程 `/grill-with-docs` 的素材——研究为思考提供素材，而不是替代思考。
- **`/to-questionnaire`** 在阻碍你的东西不在你自己脑子里也不在代码库里、而是在**别人**那里时上场，它会写出一份问卷交给对方填写。它是 `/grill-me` 的反向：不是就主题访谈你，而是就**发送动作**（寄给谁、需要拿回什么）访谈你，并把问题对准那个缺口。回收到的东西，是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 专门处理只有**人**能完成的步骤：provisioning 基础设施、配置凭据或 CI secrets、在陌生的第三方 dashboard 上点击操作、运行一次性迁移或切换。它会生成一个交互式 bash 脚本，打开每个 URL、抓取每个值，并把它们写进 `.env` 和 GitHub secrets，从而把这件事从"每次都得向 agent 重新解释一遍"变成自动化。模型调用——agent 在撞上只有你能过的墙时会立刻伸手抓它。如果 agent 自己就能做，那就该它自己做；这个 skill 是给"人在回路中"这种情形准备的。
- **`/wait-what`** 是为"一句话没接住"准备的纠正手段。在对话中途、在任何其他 skill 之内调用它，agent 会用你缺失的上下文、把刚才那段话用通俗英语重新讲一遍，并使用 `CONTEXT.md` 里的词汇。它是事后补救；`/grill-with-docs` 是事前预防，因为早期就约定好的共同语言，才是避免 jargon 出现的根本。
- **`/teach`**：跨多个会话学习一个概念，使用当前目录作为有状态的工作区。
- **`/writing-for-agents`** 是关于如何为 agent 写文档的参考资料：skills、AGENTS.md、被指向的 docs。

## 前置条件

**`/setup-matt-pocock-skills`**：在第一次跑工程类流程之前先运行它，配置 issue tracker、分诊标签、文档布局——这些都是其他 skill 假定已经存在的设置。自定义 issue tracker 同样可以工作。
