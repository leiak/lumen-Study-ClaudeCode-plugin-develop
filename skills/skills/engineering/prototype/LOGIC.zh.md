# 逻辑原型

一个单一的、自包含的 HTML 文件（一个**可分享的 demo**），允许任何人通过点击按钮来驱动一个状态模型。在问题是关于**业务逻辑、状态转换或数据形状**时使用：这种问题在纸面上看起来合理，但只有当你把它推过真实场景后才会感觉不对。

因为它是一个无需安装的文件，你可以把它交给非开发者（设计师、PM、领域专家），让他们自己感受模型。所以它说的是他们的语言，而不是代码的语言。

## 何时这是正确的形态

- "我不确定这个状态机是否处理 X 然后 Y 的边界情况。"
- "这个数据模型实际上让我能表示...的情况吗？"
- "我想在写之前感受一下 API 应该长什么样。"
- 任何有人想要**按按钮并观察状态变化**的情况。

如果问题是 "这应该长什么样"，那就走错了分支。使用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你要打样的状态模型以及什么问题。在 demo 顶部写一段（在可见的引言中，而不仅仅是注释里）。一个回答错误问题的逻辑原型纯属浪费，所以把问题明确化以便以后核对，无论用户现在在看还是 AFK 后回来。

### 2. 在可移植模块中隔离逻辑

把实际逻辑（正在回答问题的那部分）放到一个 `<script>` 块中，作为一个小的、纯净的模块来编写，这样以后可以把它拿出来放进真实代码库。围绕它的页面是临时的；这个模块不是。

正确的形态取决于问题：

- **纯 reducer**：`(state, action) => state`。当动作是离散事件且状态是单一值时很合适。
- **状态机**：显式状态和转换。当 "当前哪些动作是合法的" 是问题的一部分时很合适。
- **在普通数据类型之上的一小组纯函数。** 当没有隐式的当前状态、只有转换时很合适。
- **具有清晰方法表面的类或模块**，当逻辑确实拥有持续的内部状态时。

挑选最贴合所问问题的形态，*而不是*最易于接到页面的形态。保持纯净：没有 DOM、没有 `document`、没有触及它的按钮处理器。页面调用它；没有反向流动。这就是让原型在自身生命周期之后仍然有用的原因：一旦问题被回答，经过验证的 reducer / 状态机 / 函数集就会自己被提升到真实模块中。

### 3. 构建可分享的 HTML 文件

一个文件，普通的 HTML / CSS / JS：没有框架、没有 bundler、没有服务器，全部内联，这样它双击即可打开并能通过电子邮件传来传去。任何人都应该能通过打开它来运行它。

为非开发者编写它。每个标签都使用**领域语言**，而不是代码：按钮和状态读起来像业务，而不是 reducer。用通俗的话解释正在发生什么。

以干净的层次结构自上而下布局：

1. **标题和一句话说明**，解释这个 demo 让你探索什么（步骤 1 中的问题）。
2. **当前状态**：完整的相关状态，作为可读面板呈现（带标签的字段，而不是原始 JSON 转储），在每次点击后重新渲染，使变化可见。在有助于非开发者跟进的地方，指出刚刚发生了什么变化。
3. **自由玩按钮**：每个动作一个按钮，始终可用，以便任何人可以按任何顺序戳这个模型。每次点击都会派发它的动作并重新渲染状态。
4. **引导演练**：一组**场景**，每个选项卡一个。每个选项卡持有该场景的简短通俗描述（它设置的情况以及要注意什么），下方是针对该场景要按的有序**按钮**。每一步都是一个真实的按钮：单击它执行该动作并进入下一步。开始一个演练会将状态重置为已知的初始状态，以便每次都以相同方式运行场景。

选择能演示那些在纸上难以推理的棘手情况的场景：happy path、棘手的边界情况、尝试某种应该是非法的动作。

保持它美观但克制：干净的字体、宽松的间距、一种强调色。没有动画、没有花招：没有东西与状态和按钮竞争。

### 4. 交付给他们

把文件发送给他们，或为他们打开它。他们会在有空时点击通过演练和自由玩；有趣的时刻是他们说 "等等，那不应该可能" 或 "嗯，我以为 X 会不同"；那些是*想法*中的 bug，这才是重点。如果他们想要新的动作或新的场景，就添加它们。原体会演化。

### 5. 捕获答案和原型

一旦原型已经回答了它的问题，捕获答案，然后按 [SKILL](SKILL.md) 所述的方式捕获原型。逻辑特定的映射：经过验证的 reducer / 状态机 / 函数集被提升到真实模块（决策，已吸收）；HTML 外壳跟到保留原型的 throwaway 分支，作为主源，因为它是单个自包含文件，所以它在那里仍然可以平凡地重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型了。
- **不要把它接到真实数据库。** 使用内存状态，除非问题专门关于持久化。
- **不要泛化。** 没有 "如果我们以后想支持 X 怎么办"。原型回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可提升。让页面成为纯模块的薄外壳。
- **不要去拿框架、bundler 或服务器。** 收件人双击的一个文件；React 应用或 dev server 违背了 "可分享" 的初衷。
- **不要把 HTML 外壳发布到生产。** 该页面针对被手工点击进行了优化。它背后的逻辑模块才是值得保留的部分。
