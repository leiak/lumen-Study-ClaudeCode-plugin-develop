# UI 原型

为单一路由生成**几种截然不同的 UI 变体**，可从浮动底部栏切换。用户可以在浏览器中翻看变体，选择一个（或从每个中偷取片段），然后扔掉其余的。

如果问题是关于逻辑 / 状态，而不是某物的外观，那就走错了分支。使用 [LOGIC.md](LOGIC.md)。

## 何时这是正确的形态

- "这个页面应该长什么样？"
- "我想在承诺之前看看这个 dashboard 的几个选项。"
- "试试 settings 屏幕的不同布局。"
- 任何用户本来要花一天时间在脑海里三个模糊的 mockup 之间挑选的情况。

## 两种子形态：强烈偏好子形态 A

当一个 UI 原型**与 app 的其他部分紧密相邻**时，更容易判断：真实的 header、真实的 sidebar、真实的数据、真实的密度。独立的一次性路由是一个真空：每个变体单独看都还可以。只要有可能存在的现有页面来承载变体，就默认为子形态 A。只有当原型确实没有就近的位置时，才退而求其次选择子形态 B。

### 子形态 A：调整现有页面（首选）

该路由已存在。变体在**同一路由**上渲染，由 `?variant=` URL search param 控制。已有的数据获取、参数和 auth 都保持不变。只有渲染部分会切换。这是默认选择；除非有具体理由不选它，否则选它。

如果原型是为某个还没有页面但*自然应该存在于一个页面内*的东西（新 dashboard 区、settings 屏幕上的新卡片、现有流程中的新步骤），那仍然是子形态 A。把变体挂载到宿主页面内。

### 子形态 B：新页面（最后手段）

仅在被原型化的东西确实没有现有页面可以容纳时（例如全新的顶层界面，或无法合理嵌入任何地方的流程），才使用此选项。

按照项目已经在使用的路由约定创建一个**一次性路由**。不要发明新的顶层结构。让名字明显是原型（例如在路径或文件名中包含 `prototype` 一词）。同样的 `?variant=` 模式。

在承诺子形态 B 之前，理智检查一下：真的没有现有页面可以嵌入吗？空路由会隐藏有数据的路由会暴露的设计问题。

在两种子形态中，浮动底部栏是相同的。

## 流程

### 1. 陈述问题并挑选 N

默认为**3 个变体**。超过 5 个就不再是截然不同，而开始成为噪音，所以上限就放在那里。

在一行中写下计划，放在原型的位置或文件顶部注释中：

> "settings 页面的三个变体，可通过 `?variant=` 在现有的 `/settings` 路由上切换。"

无论用户是否在场推动，这都有效。

### 2. 生成截然不同的变体

起草每个变体。每个变体都要坚持：

- 页面的目的和它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，无论什么）。
- 一个清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层次、不同的主要可操作性，而不仅仅是不同的颜色。三个略微调整的卡片网格不是 UI 原型，那是壁纸。如果两个草稿太相似，用明确的 "不要使用卡片网格" 指导重做一个。

### 3. 把它们连起来

在该路由上创建一个单一切换器组件：

```tsx
// 伪代码，适应项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：把所有现有的数据获取保留在切换器之上；只有渲染子树按变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

屏幕底部居中一个小的固定位置栏，包含三个部分：

- **左箭头**：循环到上一个变体（环绕）。
- **变体标签**：显示当前变体键，如果变体导出了一个名字，也显示该名字。例如 `B (Sidebar layout)`。
- **右箭头**：向前循环（环绕）。

行为：

- 单击箭头会更新 URL search param（使用框架的 router，例如 Next 上的 `router.replace`，React Router 上的 `navigate` 等），以便变体可分享且重新加载后稳定。
- 键盘：`←` 和 `→` 箭头键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截箭头键。
- 视觉上与页面区分开（例如高对比度胶囊、微妙阴影），让它显然不属于被评估的设计。
- 在生产构建中隐藏：通过 `process.env.NODE_ENV !== 'production'` 或等效检查作为门控，这样原型意外合并也不会把栏带到用户面前。

将切换器放在一个共享组件中，这样两种子形态都可以重用它。把它放在项目中共享 UI 所在的位置。

### 5. 交付

把 URL（以及 `?variant=` 键）展示出来。用户会在有空时翻看。有趣的反馈通常是 **"我想要 B 的 header 和 C 的 sidebar"**，那才是他们真正想要的设计。

### 6. 捕获答案并清理

一旦某个变体获胜，捕获答案（哪个变体以及为什么），然后按 [SKILL](SKILL.md) 所述的方式捕获原型。将赢家合并到真实代码中，将其它的移到 throwaway 分支，而不是 main：

- **子形态 A**：将赢家合并到现有页面；从 main 中删除落败的变体和切换器。
- **子形态 B**：将获胜的变体提升为真实路由；从 main 中删除一次性路由和切换器。

完整的变体集合是主源，所以它落在 throwaway 分支上，而不是垃圾桶，因为留在 main 分支的变体组件和切换器很快就会腐烂并让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是调整，不是原型。真正的变体在结构上有分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 违背了初衷。每个变体都应该可以自由丢弃布局。
- **把变体接到真实的 mutation。** 只读的原型没问题。如果一个变体需要变更，指向一个 stub：问题是 "这应该长什么样"，而不是 "后端能不能工作"。
- **直接把原型提升到生产。** 变体代码是在原型约束下编写的（没有测试、最少的错误处理）。在合并进来时正确地重写它。
