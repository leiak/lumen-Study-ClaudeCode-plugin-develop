# Prototype

一个原型是**回答问题的一次性代码**。问题决定形状。

## 选择分支

通过用户的提示、周围代码，或在用户在场时询问，来识别正在被回答的问题：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个单一的可分享 HTML 文件（自由玩按钮加上选项卡式引导演练），把状态机推过那些在纸上难以推理的情况，并且非开发者也能驱动它。
- **"这应该长什么样？"** → [UI.md](UI.md)。为单一路由生成几种截然不同的 UI 变体，可通过 URL search param 和一个浮动的底部栏切换。

两个分支产出的工件非常不同，因此搞错了这一点就浪费了整个原型。如果问题确实模糊且用户不在场，默认选择与周围代码更匹配的分支（后端模块 → logic；页面或组件 → UI）并在原型的顶部说明假设。

## 适用于两者的规则

1. **从第一天起就是一次性的，并清楚地标记。** 将原型代码放在将要实际使用它的位置附近（紧挨着它所为之打样的模块或页面），这样上下文就很明显，但要命名让随意的读者可以看到它是原型而非生产。对于一次性的 UI 路由，遵守项目已经在使用的路由约定；不要发明新的顶层结构。
2. **易于运行。** UI 原型从项目 task runner 的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是一个用户双击的单一 HTML 文件。无论哪种方式，启动它不需要思考。
3. **默认无持久化。** 状态保存在内存中。持久化是原型正在*检查*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，则使用 scratch DB 或具有清晰 "PROTOTYPE, wipe me" 名称的本地文件。
4. **跳过打磨。** 没有测试，没有让原型*可运行*以外错误处理，没有抽象。重点是快速学到一些东西。
5. **暴露状态。** 在每个动作（逻辑）之后或在每次变体切换（UI）时，打印或渲染完整的相关状态，以便用户能看到发生了什么变化。
6. **完成后捕获它。** 将任何经过验证的决策合并到真实代码中，然后将原型本身作为**主源**捕获：提交到一个 throwaway 分支，不在 main 上，并在实现的 issue 上留下指向该分支的上下文指针。也将答案（结论和它所决定的问题）捕获到 issue 或 commit 中。main 分支只保留经过验证的决策。
