# 诊断 Bug

处理棘手 bug 的纪律。除非有明确理由，否则不要跳过任何阶段。

在探索代码库时，读 `CONTEXT.md`（若存在）以建立相关模块的清晰心智模型，并查看你正在改动区域的 ADR。

## Redact（脱敏）

这份 skill 会让你展示命令、输出与捕获到的产物。**先把每一条密钥脱敏**：把密钥替换为 `<REDACTED>`。围绕环境变量构建循环，使凭据始终留在环境中，而不会出现在你展示的内容里。捕获的产物带有鉴权 header：只引用那些承载信号的行。

如果脱敏后的输出不足以诊断 bug，请说明，并向用户询问。

## 第 1 阶段：构建反馈环

**这才是这份 skill 的核心。**其余都只是机械动作。如果你有一个**紧凑的**针对该 bug 的 pass/fail 信号（一条在这个 bug 上**会变红**的信号），你就能找到根因；二分、假设检验、插桩都只是消化它。如果没有，再怎么盯代码也救不了你。

在这里投入不成比例的精力。**要激进。要敢想。拒绝放弃。**

### 按大致这个顺序构建反馈环的方法

1. 在能到达 bug 的任何接缝上的**失败测试**：unit、integration、e2e。
2. 对运行中的 dev server 的 **curl / HTTP 脚本**。
3. 带 fixture 输入的 **CLI 调用**，把 stdout 与已知的良好快照 diff。
4. **Headless browser 脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM / console / network 做断言。
5. **回放捕获到的 trace。** 把一个真实的网络请求 / payload / event log 存到磁盘；在隔离状态下用其代码路径回放。
6. **一次性 harness。** 启动系统的一个最小子集（一个服务、mock 的依赖），让它用一次函数调用就走过 bug 代码路径。
7. **Property / fuzz 循环。** 如果 bug 是"输出有时候错"，跑 1000 次随机输入，去找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、dataset、version），自动化"在状态 X 启动，检查，重复"，让你能 `git bisect run` 它。
9. **差分循环。** 把同一份输入跑过旧版 vs 新版（或两种配置），diff 输出。
10. **HITL bash 脚本。** 兜底。如果必须由人来点击，用 `scripts/hitl-loop.template.sh` 去**驱动他们**，让循环仍然是结构化的。捕获到的输出再喂回给你。

搭对了反馈环，bug 就算修好 90% 了。

### 收紧循环

把循环当作一个产品。一旦有了**一个**循环，就去**收紧**它：

- 我能让它更快吗？（缓存 setup、跳过无关 init、收窄测试范围。）
- 我能让信号更尖锐吗？（断言具体的症状，而不是"没崩"。）
- 我能让它更确定吗？（固定时间、播种 RNG、隔离文件系统、冻结网络。）

一个 30 秒还 flaky 的循环，几乎等于没有循环；一个 2 秒确定的循环才算紧凑，才叫调试超能力。

### 非确定性 bug

目标不是一个干净的复现，而是一个**更高的复现率**。把触发条件循环 100 次，并行化、加压、收窄时间窗、注入 sleep。一个 50% flaky 的 bug 是可调的；1% 不可调，所以把复现率一路拉到可调为止。

### 当你确实搭不出循环时

停下来明确说出来。把试过的事列出来。向用户请求：(a) 访问任何能复现该 bug 的环境，(b) 一份脱敏后的捕获产物（HAR 文件、log dump、core dump、带时间戳的录屏），或 (c) 允许加入临时的生产插桩。**不要**在没有循环的情况下去做假设。

### 完成准则：一条紧凑且会变红的循环

当循环**紧凑**且**会变红**，第 1 阶段就完成了：你能说出**一条命令**（一个脚本路径、一次测试调用、一次 curl），并且你已经**至少跑过一次**（展示该调用与它的脱敏后输出），它满足：

- [ ] **会变红**：它驱动实际的 bug 代码路径，并断言**用户的具体症状**，因此能在本 bug 上变红、并在修好后变绿。不是"运行没出错"；它必须能**逮到这只具体的 bug**。
- [ ] **确定性**：每次跑出同样的判定（flaky 的 bug：按上面的要求，做到固定的高复现率）。
- [ ] **快速**：秒级，而不是分钟级。
- [ ] **Agent 可跑**：你可以无人值守地跑它；只有通过 `scripts/hitl-loop.template.sh` 才把"人"放进回路。

如果你发现自己在"先读代码、再建理论"，而这条命令还不存在，**停下来：跳到假设正是这份 skill 防止的失败。**没有会变红的命令，就没有第 2 阶段。

## 第 2 阶段：复现 + 最小化

跑循环。眼睁睁看着它变红，bug 出现。

确认：

- [ ] 循环产出的失败模式就是**用户**描述的那种，而不是"恰好在旁边"的不同失败。修错 bug = 修错地方。
- [ ] 失败在多次运行下可复现（或对非确定性 bug 而言，以足够高的频率可复现、可被调试）。
- [ ] 你已经捕获到精确的症状（错误消息、错误输出、慢在哪），以便后续阶段能验证修复确实解决了它。

### 最小化

一旦红了，就把复现缩到**仍然会变红的最小场景**。**一次一个地**砍输入、调用者、配置、数据与步骤，每次砍完重跑循环，只留下对失败承重的部分。

为什么值得做：最小化的复现把第 3 阶段的假设空间缩小（剩下的可怀疑部件更少），它还会变成第 5 阶段中干净的回归测试。

**剩下的每个元素都是承重的**时算完成：把其中任何一个拿掉，循环就会变绿。

在完成**复现 + 最小化**之前，不要往下走。

## 第 3 阶段：做假设

在测试任何假设之前，先提出**3–5 个排序后的假设**。只生成一个假设会让你锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式："If <X> is the cause, then <changing Y> will make the bug disappear / <changing Z> will make it worse."

如果你说不出预测，这条假设就是个 vibe：丢掉它，或把它磨锋利。

**在测试之前，把排序后的清单展示给用户。**他们常常拥有领域知识，能立刻重排（"我们刚部署了 #3 的变更"），或知道已经被排除掉的假设。这是一道便宜的检查点，能省下大量时间。别在它上面阻塞；如果用户 AFK 就按你排的继续。

## 第 4 阶段：插桩

每条探针必须对应到第 3 阶段里某个具体的预测。**一次只改一个变量。**

工具偏好：

1. **Debugger / REPL inspection**（如果环境支持）。一个断点胜过十条 log。
2. **针对性 log**，放在能区分假设的边界上。
3. 永远不要"log everything and grep"。

**给每条 debug log 打上唯一前缀**，如 `[DEBUG-a4f2]`。最后清理时一次 grep 就完事。没打标签的 log 会活下来，打了标签的会死掉。

**Perf 分支。** 对性能回归，log 通常没用。正确做法：先建立基线测量（timing harness、`performance.now()`、profiler、query plan），再二分。先测，再修。

## 第 5 阶段：修复 + 回归测试

把回归测试**写在修复之前**，但前提是存在一个**正确的接缝**。

正确的接缝是这样的：测试按 bug 在 call site 上发生的形态，去演练**真实的 bug pattern**。如果唯一可用的接缝太浅（bug 需要多个 caller 时却只有单 caller 测试、单元测试复刻不出触发 bug 的那条链），放在那里的回归测试只会给你虚假的信心。

**如果不存在正确的接缝，那本身就是发现。**记下来。代码库架构正在阻止把这个 bug 锁死。在下一阶段标记这点。

如果存在正确的接缝：

1. 把最小化后的复现变成那条接缝上的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 用第 1 阶段的反馈环，对原始（未最小化）的场景再跑一次。

## 第 6 阶段：清理

宣布完成之前必须做：

- [ ] 原始复现不再复现（重跑第 1 阶段的循环）
- [ ] 回归测试通过（或者在缺少接缝时把这点写明）
- [ ] 所有 `[DEBUG-...]` 插桩都已移除（grep 那个前缀）
- [ ] 一次性原型已删除（或搬到一处明显标记为 debug 的位置）
- [ ] 真正成立的那条假设写在 commit / PR 描述里，让下一个调试者能学到
