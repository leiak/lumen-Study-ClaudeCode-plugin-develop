# 测试驱动开发

TDD 是 red → green（红到绿）的循环。这个 skill 是一份参考资料，让这个循环产出的测试值得保留：什么是好的测试、测试放在哪里、反模式、循环的规则。每个段落都适用于每一个循环：在循环前和循环中查阅它们，而不是循环之后。

在探索代码库时，读取 `CONTEXT.md`（如果存在），让测试名和接口词汇与项目的领域语言一致，并尊重你所触及区域的 ADR。

## 什么是好的测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应改变。一个好的测试读起来像一份规范说明："user can checkout with valid cart" 精确地告诉你存在什么能力，并且因为它不关心内部结构，所以它能在重构中存活下来。

示例参见 [tests.md](tests.md)，mocking 指南参见 [mocking.md](mocking.md)。

## Seams：测试放在哪里

**seam** 是你测试所在的公共边界：你在不触及内部的情况下观察行为的接口。测试位于 seam 处，绝不针对内部。

**只在预先约定的 seam 上测试。** 在编写任何测试之前，先写下要测试的 seam 并与用户确认。未经确认的 seam 上不写任何测试。你不可能测试所有东西，所以提前约定 seam 是让测试精力集中在关键路径和复杂逻辑上、而不是每个边界情况的方式。

问："公共接口是什么，我们应该测试哪些 seam？"

当该接口的形态本身成问题时（模块的深度、seam 属于哪里、接口应暴露什么），用 Skill 工具调用 "codebase-design" 以获取词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同来源，它是一份可以查阅的参考资料，而不是要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过侧通道验证（查询数据库而不是使用接口）。特征：当你重构但行为没有变化时，测试就会坏掉。
- **同义反复**：断言以与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工推导的快照、常量断言等于自身），所以它按构造就通过，永远不可能与代码不一致。期望值必须来自独立的真相来源：已知的字面量、已演算的示例、规范。
- **横向切片**：先写所有测试，再写所有实现。批量测试验证的是*想象中的*行为：你测试的是事物的*形状*而不是面向用户的行为，测试对真实变化失去敏感，并且在理解实现之前就承诺了测试结构。改为以**纵向切片**工作：一个测试 → 一个实现 → 重复，每个测试都是对上一个循环教给你的东西做出响应的**示踪弹**。

## 循环的规则

- **先红后绿。** 先写失败测试，再写刚好让它通过的代码。不要预期未来的测试或添加投机性功能。
- **一次一个切片。** 每个循环一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于 review 阶段（参见 `code-review` skill），不属于 red → green 的实现循环。
