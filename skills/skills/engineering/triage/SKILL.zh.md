# Triage

让项目 issue tracker 上的 issue 在一个小巧的分诊角色状态机中流转。

如果本仓库把外部 pull request 视作请求面（见 issue-tracker 配置），triage 也覆盖它们：**PR 是一张挂着代码的 issue**，用同样的角色、同样的状态、同样的机器，差异点在文中"for a PR"处标注。按 tracker 配置把一个裸的 `#42` 解析为 issue 或 PR。

在 triage 期间发到 issue tracker 的每一条评论或 issue **都必须**以这条声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写出持久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两条 **category（类目）** 角色：

- `bug`：什么东西坏了
- `enhancement`：新功能或改进

五条 **state（状态）** 角色：

- `needs-triage`：维护者需要评估
- `needs-info`：在等报告人提供更多信息
- `ready-for-agent`：完全规格化、可被 AFK agent 接走
- `ready-for-human`：需要人来实现
- `wontfix`：不会被处理

对 PR 而言，同样的状态对应到所挂的代码读：`ready-for-agent` 意味着已附一份 brief，由 agent 接手 diff 的下一步；`ready-for-human` 意味着已经准备好由人来合并。

每条被分诊的 issue 应恰好携带一个类目角色和一个状态角色。如果状态角色冲突，先标出来、询问维护者，再做任何其他事。

这些是规范化的角色名。issue tracker 中实际使用的标签字符串可能不同。映射关系应当已经提供给你。如果还没有，告诉用户去运行 `/setup-matt-pocock-skills`。

状态转移：未打标签的 issue 通常先进入 `needs-triage`；从此可转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告人回复后回到 `needs-triage`。维护者可以在任何时候覆盖；遇到看起来异常的转移，先标出来、再询问，之后再继续。

## 调用

维护者调用 `/triage`，并用自然语言描述他想要的事。解释请求并执行。例子：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要注意的事

查询 issue tracker，按从旧到新的顺序呈现三个桶：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且报告人在上一次 triage notes 之后有活动**：需要重新评估。

当 PR 也在范围内时，把外部 PR 也归入这些桶，并给每一行标 `[PR]` 或 `[issue]`。发现流程只暴露**外部** PR（tracker 配置定义"谁算外部"），所以合作者正在推进中的 PR 不算 triage 工作。这道筛选只用于发现阶段；显式指名的 PR 无论作者是谁都会被 triage。

展示每条的计数与一行简介。让维护者来挑选。

## 对一条具体的 issue 或 PR 进行 triage

1. **收集上下文。** 读完整条 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析之前任何 triage notes，避免重提已解决的问题。借助项目的领域词表、并尊重相关区域的 ADR 来探索代码库。运行两项基于代码库的检查：(a) **冗余**：按"领域概念"（而非请求的措辞）搜索是否已经实现了请求中的行为，并报告你搜过哪里。如果发现，那就是一条"已实现"的 `wontfix`（第 5 步）。(b) **历史否决**：读取 `.out-of-scope/*.md`，把与本请求相似的条目拎出来。
2. **给出建议。** 把你的类目与状态建议及理由告诉维护者，并附上一段与请求相关的代码库摘要（包括是否已经实现）。等待指示。
3. **核实主张。** 在任何访谈之前，先确认主张成立。bug：按报告人的步骤复现。PR：确认 diff 确实做了它声称的事 —— 把它 checkout 出来、跑相关测试或命令。报告结果：已确认（附代码路径）、失败、或细节不足（一个强烈的 `needs-info` 信号）。一条经过确认的核实结果，会让 agent brief 强得多。
4. **访谈（如有需要）。** 如果请求还需要被补全，调用 Skill 工具两次，分别对应 "grilling" 和 "domain-modeling"，并一轮一轮地把它访谈成形，同时随着每个决策落定，锐化领域术语、就地更新 `CONTEXT.md` / ADR。
5. **落实结果：**
   - `ready-for-agent`：发一条 agent brief 评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent brief 相同，但要注明为什么不能委派（判断题、外部访问、设计决策、人工测试）。
   - `needs-info`：发 triage notes（见下方模板）。
   - `wontfix`：关闭 issue，评论取决于**为什么**：
     - **已实现**：代码里已经有这项变更。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是为"被否决的"请求准备的，不是"已实现的"）。
     - **被否决（bug）**：礼貌地解释，然后关闭。
     - **被否决（enhancement）**：写入 `.out-of-scope/`，评论里附上链接，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上该角色。如果有部分进展，可选地加一条评论。

## 快速状态覆盖

如果维护者说"move #42 to ready-for-agent"，相信他、直接打上该角色。先确认你即将做的事（角色变更、评论、关闭），然后再行动。跳过访谈。如果直接移到 `ready-for-agent` 而没有访谈一轮，问问他是否想写一份 agent brief。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把访谈过程中已经解决的每一项都收进"established so far"，避免工作丢失。问题必须具体且可行动，不要写"please provide more info"。

## 接着上一次的会话继续

如果 issue 或 PR 上已存在 triage notes，先读它们，检查报告人是否回答了任何未决的问题，并展示一份更新后的画面，再继续。不要重提已经解决的问题。
