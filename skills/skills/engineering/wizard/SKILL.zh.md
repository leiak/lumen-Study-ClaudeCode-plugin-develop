# Wizard

一个 **wizard** 是一段 bash 脚本，逐步引导人类完成一项手工过程，这项手工过程手动做起来很繁琐，每次都要重新给 AI 解释也很繁琐。它打开每个 URL，准确说出要点击和复制的内容，捕获这些值，把它们写到所属的位置（`.env`、GitHub secrets），在每个阶段进行确认，并显示还剩多少阶段。它可能配置第三方服务、运行一次性迁移，或将项目从一个状态移到另一个状态。

良好的用户体验已由 [template.sh](template.sh) 解决：阶段式进度、确认门、跨平台 URL 打开（包括 WSL）、隐藏的 secret 输入、对 `.env` 的幂等 upsert、`gh secret` / `gh variable` 写入，以及结束的总结。**你的工作只是界定过程的边界并撰写它的各阶段。** `STAGES` 标记之上的库在每个 wizard 中都相同；这种一致性才是重点：永远不要手工编辑它。

默认情况下 wizard 是临时的：为一次运行而构建，保存在 scratch 或 `scripts/` 路径下，工作完成后删除。仅当用户希望有一个应该存放在仓库中的可重复设置路径时才提交它。

## 流程

### 1. 界定过程的范围

弄清楚人类必须执行的每个手工步骤以及沿途捕获的每个值。先阅读仓库，不要凭空问：

- 对于 setup：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是 wizard 必须产出的值）。
- 对于迁移或过渡：当前状态、目标状态，以及它们之间的不可逆动作。

然后向用户展示按顺序排列的阶段列表以及每个阶段产生的值，并确认：他们可以添加、删除或重新排序。

**完成时：** 每个阶段按顺序命名，并且对于每个捕获的值，你都知道 (a) 人类从哪里获得它，(b) 它被写到哪里（`.env`、一个 GitHub secret、两者、或者不写；有些阶段是纯动作），以及 (c) 它是否是 secret（隐藏输入）还是公开的。

### 2. 描绘每个阶段的路径

对于每个阶段，写下人类所走的精确路径：打开哪个 URL、在那里做什么、值在哪里显示、它填入哪个变量：例如 "Dashboard → Developers → API keys → Reveal test key → copy"。在你实际上不知道当前 UI 或确切命令的地方，说明并询问用户或查阅文档：永远不要编造可能不存在的步骤。

**完成时：** 每个阶段都能追溯到陌生人也能遵循的具体指令。

### 3. 编写 wizard

将 `template.sh` 复制到目标路径。按依赖顺序用每个步骤的一个 `stage` 替换示例 stage。使用库帮助器：`stage`、`say` / `step`、`open_url`、`ask` / `ask_secret`、`write_env`、`set_secret` / `set_var`、`pause` / `confirm`。将 `TOTAL_STAGES` 设置为你编写的阶段数。

维持模板设定的标准：在询问 URL 的值之前先打开它，对任何 secret 使用 `ask_secret`，对每个持久化的值使用 `write_env`，只对 CI 真正需要的值使用 `set_secret`，在任何不可逆动作之前使用 `confirm`。每个 `stage` 都会清屏，让只有当前步骤可见：让一个阶段保持一项聚焦任务，这样人类需要的东西不会被滚动掉。不要触及标记之上的库。

### 4. 验证和交接

- `bash -n <script>`；如果可用则运行 `shellcheck`。
- `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器并阻塞在人类输入处。改为静态跟踪它：步骤 1 中的每个值都被捕获并落在步骤 1 指定的位置，并且每个 `set_secret` 名称都与 CI 中的 `secrets.*` 引用完全匹配。
- 告诉用户如何运行它。如果它是可重复的设置路径，则提交它并从 README 链接它，这样下一个人运行脚本而不是去问 AI。
