# 领域建模

在设计过程中积极构建并打磨项目的领域模型。这是一种*主动*的纪律：挑战术语、构造边界场景的假设、并在术语和决策一旦清晰就立刻记入词汇表和决策记录。（仅仅是*阅读* `CONTEXT.md` 来查词不是这个 skill：那是任何 skill 都能做到的一行习惯。这个 skill 用于你正在改变模型的时候，而不只是消费它的时候。）

## 文件结构

大多数仓库有单一的 context：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则该仓库有多个 context。map 指向每个 context 所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                 ← context 特有决策
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

按需懒创建文件：只有当有东西要写时才创建。如果不存在 `CONTEXT.md`，则在第一个术语确定下来时创建一个。如果不存在 `docs/adr/`，则在需要第一个 ADR 时创建。

## 会话期间

### 挑战词汇表

当用户使用的术语与 `CONTEXT.md` 中已有语言相冲突时，立即指出。"你的词汇表把 'cancellation' 定义为 X，但你似乎指的是 Y。到底是哪个？"

### 打磨模糊的语言

当用户使用模糊或重载的术语时，提出一个精确的规范术语。"你说的是 'account'：你指的是 Customer 还是 User？那是两回事。"

### 讨论具体场景

当领域关系正在被讨论时，用具体的场景去压力测试它们。构造能探查边界条件、迫使用户对概念之间的边界做出精确表述的场景。

### 与代码交叉验证

当用户陈述某件事如何工作时，检查代码是否一致。如果你发现矛盾，揭示它："你的代码取消了整个 Order，但你刚才说部分取消是可能的。哪个是对的？"

### 内联更新 CONTEXT.md

当一个术语确定下来时，立刻更新 `CONTEXT.md`。不要把这些攒起来：发生时立即捕获它们。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不含实现细节。不要把 `CONTEXT.md` 当成规范说明、草稿本或实现决策的仓库。它只是一份词汇表，仅此而已。

### 谨慎地提供 ADR

仅当以下三点全部成立时才主动提议创建 ADR：

1. **难以逆转**：以后改变主意的代价很大
2. **脱离上下文会令人意外**：未来的读者会想知道"他们为什么这么做？"
3. **真正的权衡的结果**：存在真正的替代方案，而你出于具体原因选择了其中一个

如果三者缺一，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
