# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

按需懒创建 `docs/adr/` 目录：只有在需要第一个 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们做了什么决策，以及为什么。}
```

仅此而已。一个 ADR 可以是一段话。其价值在于记录*做出了什么*决策以及*为什么*，而不是填写各章节。

## 可选章节

仅当它们确实增加价值时才包含。大多数 ADR 都不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决策被重新审视时很有用
- **Considered Options**：只有在被否决的替代方案值得记住时才包含
- **Consequences**：只有在需要指出不明显的下游影响时才包含

## 编号

扫描 `docs/adr/` 找到当前最大的编号，再加一。

## 何时提议创建 ADR

以下三点必须全部成立：

1. **难以逆转**：以后改变主意的代价很大
2. **脱离上下文会令人意外**：未来的读者看到代码时会想知道"他们到底为什么要这么做？"
3. **真正权衡的结果**：存在真正的替代方案，而你出于具体原因选择了其中一个

如果一个决策容易逆转，就跳过：你会直接逆转它。如果不令人意外，没人会想知道为什么。如果没有真正的替代方案，那就只值得记录"我们做了显而易见的事"。

### 哪些内容符合条件

- **架构形态。** "我们使用 monorepo。" "写模型是事件溯源的，读模型被投影到 Postgres。"
- **context 之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库：只是那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据归 Customer context 所有；其他 context 只通过 ID 引用它。" 明确的否定与肯定同样有价值。
- **对显而易见路径的有意偏离。** "我们使用手写 SQL 而非 ORM，因为 X。" 任何合理读者会假设相反的情况。这些会阻止下一位工程师去"修复"原本是有意为之的东西。
- **代码中看不见的约束。** "因为合规要求我们不能使用 AWS。" "因为合作方 API 契约，响应时间必须低于 200ms。"
- **当否决理由不明显时记录被否决的替代方案。** 如果你考虑过 GraphQL 却出于微妙的原因选择了 REST，请记录它；否则六个月后有人会再次建议 GraphQL。
