用户请求了一次**回顾（retrospective）**。你正在为编码 agent 的**环境**提出改进建议，以改进未来的运行。

## 步骤

1. 调用 Skill 工具，使用 `writing-for-agents` 获取写作风格指南。

2. 阅读用户指定会话的主要来源。这可能意味着要在这台机器上搜索会话日志。如果用户没有指定会话，则默认为当前会话。

3. 在以下类别中寻找改进候选。

- **导航（Navigation）**：agent 找到正确文件的难易程度如何？文件之间是否存在隐藏的依赖关系？一个**导航指针（navigation pointer）**能否让事情变得更容易？_适用于_会话花了很长时间才找到某条信息的情况。
- **自动化检查（Automated checks）**：是否存在可以捕捉到 agent 所犯错误的自动化检查？lint、类型检查、测试、文件系统 linter？_适用于_agent 犯下的错误本可被自动化检查捕捉到的情况。
- **编码规范（Coding standards）**：是否应该给**reviewer agent**一条新规则来强制执行？是否应该移除或澄清一条现有规则？_适用于_reviewer agent 未捕捉到某个错误的情况。
- **全局 AGENTS.md**：是否有一些指导指令应当移到编码规范（或自动化检查）中？_适用于_`AGENTS.md` 文件特别庞大的情况，无论是在 repo 内还是用户的全局范围内。
- **工具经济性（Tool economy）**：agent 是否进行了可以精简的高开销工具调用？是否存在某些自定义工具（CLI、MCP）特别消耗 token？_适用于_agent 进行了高开销工具调用的情况。
- **无效指令（No-ops）**：查找那些不会改变 agent 行为的指导文件中的指令。_适用于_指导文件大而笨重的情况。
- **信息访问（Information access）**：寻找增加 agent 信息访问的机会。捕获 dev server 的日志、对第三方服务的只读访问。_适用于_agent 缺少关键信息的情况。

4. 按严重程度向用户呈现这些候选。

## 参考

### 实现与审查

请记住，所有工作都经过两个阶段：实现和审查。实现 agent 承担最大的**上下文压力**。它负责探索、编写代码以及调试失败。

review agent 承担的上下文压力最小，它接收一个 diff，因此不需要探索。它通常不需要写代码或调试。

这意味着 review agent 应当负责施加编码规范，而不是实现 agent。

### 文件

你可以访问 repo 中的几个文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推送到在此 repo 中工作的任何 agent 的上下文窗口中。应当极为克制地使用它们，通常只用作指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：此文件在审查期间被读取，而非实现期间。如果规范文件超过 1,000 行，可以添加指向 docs 文件夹的**导航指针**。
- Docs：将 docs 用作参考文件，由其他文件指向。在编写新文档之前，先查找现有文档。
- Skills：将 skills 用作文档（因为其描述会进入 agent 的上下文窗口），或用作用户调用的命令。遵循 `writing-for-agents` skill 中的建议。
