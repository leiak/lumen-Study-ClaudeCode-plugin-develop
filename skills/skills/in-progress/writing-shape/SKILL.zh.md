<what-to-do>

用户已传入（或将会传入）一份 markdown 原始素材文件。将其视作输入素材堆：从一份整齐的 fragments 列表，到一堵未经组织的散文墙，再到一段对话记录，形式不重要。在做任何事之前，先把它从头到尾读一遍。

然后运行一次 shaping 会话，产出单独的文章文档。这是 **exploit**：探索已完成，素材堆已固定：承诺一种结构，并从素材堆中挖掘内容来填充它。不要编辑原始素材文件：本 skill 将其视为只读。

如果用户没有说明文章保存到哪里，请询问一次并记住该路径。

</what-to-do>

<supporting-info>

## 循环

1. **阅读素材堆**。完整阅读输入文件。对其中有什么形成一个感觉。
2. **确定 prerequisites**。与用户敲定读者走进文章时已经知道的内容：那些从一开始就是 **grounded** 的概念。其他一切都必须先由一个 block grounding，然后才能被后续的 block 依赖。参见 [Grounding](#grounding)。
3. **起草 2–3 个候选开头**。每个开头都应当暗示文章不同的论点或角度。把它们都展示出来。强迫用户做出选择，或合成一个折中版本。被选中的开头决定了文章其余部分必须做什么。
4. **逐段生长**。在开头落定之后，询问"给定这个开头，读者接下来需要听到什么？"从素材堆中抽取材料来回答。下一个 block 只能依赖 grounded 的概念，并在落地时 grounding 新的概念。关于下一个 block 应采取的形式要展开讨论：一段文字、一份列表、一张表格、一个 callout、一段引文、一个 code block。每种格式选择都应当是有意且可辩护的。
5. **边推进边写入文章文件**。不要批量。每当一段落或一个 block 商定后立刻写入，让用户能看到文章正在成形。
6. **循环步骤 4 直到文章完成**。由用户决定何时结束。

## Grounding

每个**概念**都必须在某个 block 依赖它之前先被 **grounded**：读者要么走进文章时就已经知道它，要么在更早的 block 中遇到过它。一个 block 如果触及未 grounding 的概念，就会失去读者。衡量的单位是概念本身，而非它的词：即便行文中没有任何术语，一个 block 仍可能依赖读者并不具备的想法。当一个概念有一个名字（一个**术语**）时，grounding 它意味着把这个想法和这个术语一起落到位。

一个概念通过以下两种方式之一被 grounding：

- **Prerequisite**：在开头之前就已经 grounded。读者一开始就具备。在文章开头固定下来。
- **Introduced**：由某个 block 确立，从此之后对文章的其余部分都是 grounded 的。

维护一份当前已 grounding 内容的清单。当你询问"读者接下来需要听到什么？"时，下一步需要、却尚未 grounding 的概念本身就是答案：先 grounding 它（在这里或更早的某个 block 中），否则你就无法做出这一步。这是 [Pulling from the pile](#pulling-from-the-pile) 中所说 gap-naming 上一级的问题：那里是素材堆缺少材料；这里是文章缺少一个基础。

杠杆在于把哪些概念设为 prerequisite、哪些概念在文章内部 grounding。起点要求太多，会把读者挡在门外；文章内 grounding 太多，则开头会淹没在定义中。在确定 prerequisites 时与用户敲定这一点。

## 对话的调性

这是一场倒过来的 grilling 会话。在 ideation 阶段，问题是"你真正注意到的是什么？"在这里，问题是"这篇文章真正在论证什么，以及读者需要以什么顺序听到它？"要反驳。不要放过软弱过渡。如果一段没有挣到它的位置，就删掉。

可以继续使用的具体招式：

- "这段相对前一段，让读者多得到了什么？"
- "如果我删掉它，什么会崩？"
- "这是散文，还是应当是列表？为什么是散文？"
- "这句话做了两件事：要么拆开，要么只保留一件。"
- "开头承诺的是 X。我们已经漂到 Y。要么重新把它接回 X，要么改开头。"

## 从素材堆中取材

将原始素材视作 quarry，而非脚本。抽取一个 fragment，改写以适配周围的段落，再放置它。一个 fragment 可以被拆到多个段落中，也可以与另一个合并或被改写。素材堆的工作是被开采；文章的工作是读起来像一种声音。

如果素材堆缺少文章所需的内容，请明确点出这一缺口："这里需要一个例子，但素材堆里没有。现在就给我一个，否则我们就把这一节砍掉。"

## 真正值得讨论的格式之争

在选择如何呈现一个 block 时，把以下取舍和用户当面讨论，而不是默默决定：

- **散文 vs. 列表**。散文承载论证；列表承载并列项。如果各项并非真正并列，散文更好。如果确实并列，列表更易于扫读。
- **行内 vs. callout**。提示、警告和题外话放在 callout 中（`> [!TIP]`、`> [!NOTE]`），但前提是它们真的会打断主体论证。否则就留在行内。
- **表格 vs. 重复结构**。如果相同形状以相同字段重复出现 3 次以上，用表格。否则用带粗体引导词的散文。
- **引文 vs. 改述**。当原文措辞本身就是要点时用引文。当只关心观点时用改述。
- **Code block vs. inline code**。多行、可运行或具有示范意义的 → block。单个 token 或标识符 → inline。

## 写作节奏

每当一个 block 商定后，就将其追加到文章文件中。每次写入前从磁盘重新读取文件：用户可能在两轮之间进行过编辑。永远不要盲目覆盖。如果用户希望重写某一段，就地编辑该段落；其余内容不动。

## 范围之外

- 挖掘素材堆中并不存在的新 fragments（按 "Pulling from the pile" 中的方式处理缺口）。
- 编辑原始素材文件。
- 发布、为特定平台格式化，或添加用户未要求的前置元数据。
